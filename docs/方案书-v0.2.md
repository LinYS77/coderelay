# 个人验证码聚合服务方案书（v0.2）

> 状态：关键决策已确认，正在实施
> 日期：2026-07-30
> 暂定项目名：`CodeRelay`
> 目标部署环境：单用户、单台轻量 VPS、独立 Linux 可执行程序、公网 HTTPS

## 0. 结论摘要

建议将项目做成一个**只读的验证码聚合网关**：调用方只知道“来源别名”，不接触或传递上游 TOTP Secret、Outlook refresh token、FlySMS token。

推荐技术路线：

- Python 3.11+；
- FastAPI 提供 REST API、受保护的 OpenAPI 和健康检查；
- PyOTP 生成 TOTP；
- MSAL 只负责 Microsoft OAuth/token cache；
- HTTPX 直接调用 Microsoft Graph REST，**不引入体积很大的完整 `msgraph-sdk`**；
- HTTPX 直接调用 FlySMS 当前网页所使用的 JSON 接口，不做 HTML 抓取或无头浏览器；
- Jinja2 + 原生 HTML/CSS/少量 JavaScript 实现前端，不引入 React/Vite 构建链；
- 通过 PyInstaller 构建单文件 Linux 可执行程序；HTTPS 由 VPS 已有反向代理负责，不属于本项目交付；
- API Bearer Token 与网页登录凭据分离；
- 默认按需读取，不常驻轮询邮箱，不保存邮件正文。

### 真正的核心问题

这个项目的难点并不是“怎样匹配六位数字”，而是：

> 如何把三种完全不同的验证码来源统一为一个不会泄漏上游凭据、不会误返回旧验证码或错误数字、并且能在公网安全运行的接口。

因此，方案把以下三件事视为一等公民：

1. **凭据隔离**：调用方只提交本服务密钥和来源 ID；
2. **新鲜度语义**：邮件验证码必须支持 `not_before` 与有限时间等待，避免拿到上一封邮件里的旧码；
3. **可验证提取**：按发件人、时间、上下文和规则提取，歧义时宁可报错，也不静默返回错误数字。

## 1. 需求边界

### 1.1 MVP 要完成

1. 为已配置的 TOTP 来源生成当前六位验证码，并返回剩余有效秒数；
2. 从一个个人 Outlook 邮箱读取新邮件并提取六位验证码；
3. 从一个 FlySMS iCloud 取件来源读取新邮件并提取六位验证码；
4. 提供统一、版本化、带 Bearer Token 鉴权的 API；
5. 提供简洁的单用户网页：查看来源、获取验证码、复制验证码、查看状态；
6. 能构建为单文件 Linux 可执行程序，在 VPS 上以独立非 root 用户运行；公网 TLS 由现有反向代理负责；
7. 不把 TOTP Secret、邮箱 token、服务 API key、验证码和邮件正文写入普通日志；
8. 上游失效、限流、重新授权等情况有明确错误码。

### 1.2 MVP 明确不做

- 多用户、注册、找回密码、RBAC；
- 发送邮件、删除邮件、标记已读；
- 完整邮件客户端或永久保存邮件正文；
- 自动识别任意网站、任意格式的所有验证码；
- 在网页中展示或编辑 refresh token、邮箱密码、TOTP Secret；
- 依赖 Outlook 用户名/密码登录（ROPC）；
- 后台不停轮询所有来源；
- 在 URL 查询参数中传递 secret/token/API key；
- 对第三方未公开接口可用性作永久保证。

## 2. 对现有 `reference/` 的探索结论

当前目录除参考代码外尚无业务实现，也不是 Git 仓库。

### 2.1 PyOTP

相关位置：

- `reference/pyotp/README.rst`
- `reference/pyotp/src/pyotp/totp.py`
- `reference/pyotp/src/pyotp/otp.py`
- `reference/pyotp/src/pyotp/__init__.py`
- `reference/pyotp/test.py`

结论：

- PyOTP 已完整实现 RFC 6238 TOTP；默认参数正是常见的 SHA-1、6 位、30 秒；
- 支持 Base32 secret 和 `otpauth://` URI；
- 测试中包含 RFC 向量，可直接转化为本项目回归测试；
- TOTP 正确性依赖 VPS 时钟，因此部署验收必须检查 NTP/chrony；
- 不需要复制其算法源码，直接使用锁定版本的 PyPI 包即可。

### 2.2 MSAL for Python

相关位置：

- `reference/microsoft-authentication-library-for-python/README.md`
- `reference/microsoft-authentication-library-for-python/sample/device_flow_sample.py`
- `reference/microsoft-authentication-library-for-python/sample/migrate_rt.py`
- `reference/microsoft-authentication-library-for-python/msal/token_cache.py`
- `reference/microsoft-authentication-library-for-python/msal/application.py`

结论：

- 正确模式是：先从持久化 cache 静默取 token，必要时由 MSAL 自动刷新；
- Device Code Flow 很适合无浏览器 VPS 的一次性授权；
- `acquire_token_by_refresh_token()` 在 MSAL 文档中主要用于把“外部旧 refresh token”迁移进 MSAL cache，而不应成为每次请求的常规流程；
- `SerializableTokenCache` 只负责序列化，不负责安全持久化；本项目需自行处理原子写入、文件权限和可选加密；
- Outlook 账户密码不是读取 Graph 邮件所必需的，也不应保存在本服务中。

### 2.3 Microsoft Graph Python SDK

相关位置：

- `reference/msgraph-sdk-python/README.md`
- `reference/msgraph-sdk-python/docs/general_samples.md`
- `reference/msgraph-sdk-python/msgraph/generated/users/item/messages/messages_request_builder.py`

探索结果：

- 参考仓库约 313 MiB，生成文件约 15,783 个；
- 它完整支持 `$select`、`$filter`、`$orderby`、`$top`、分页等 Graph 能力；
- 但本项目只需要一两个邮件读取端点，引入完整 SDK 会增加镜像、依赖和升级面；
- 因此采用 **MSAL + HTTPX + Graph REST** 更符合“轻量服务”的目标；
- Graph 邮件接口建议使用 delegated `Mail.Read`。`Mail.ReadBasic` 不包含 `body`、`bodyPreview` 等内容，不能稳定提取正文验证码；
- 只请求需要的字段，并优先读取 Inbox，避免无关邮件和大响应。

### 2.4 FlySMS 取件页

对公开页面及其公开前端资源进行了静态检查，**没有使用对话中给出的实际 token 发请求**。

当前网页不是服务端渲染邮件，而是浏览器调用同源 JSON API。取件 URL 的 `#email=...&key=...` 属于 URL fragment，本身不会随页面请求发送给服务器；网页 JavaScript 再将其转换为请求头。

当前前端使用的接口契约如下：

```text
GET /icloud/api/pickup/messages/latest
GET /icloud/api/pickup/messages?limit=30&cursor=...
GET /icloud/api/pickup/messages/{uid}?mailbox=...
```

请求头：

```http
Accept: application/json
Authorization: Bearer <pickup-token>
X-Mailbox-Email: <mailbox-email>
```

观察到的行为：

- `latest` 返回最新邮件详情；
- 列表接口返回摘要、`nextCursor`、`scope`、`revision`，并支持 ETag；
- 当前网页识别 401、403、404、429、502、503；
- 429 可能带 `Retry-After`；
- token 形态当前为 `tok_...`；
- 无凭据访问返回结构化 401；
- 接口响应声明 `Cache-Control: no-store`。

结论：

- 服务端可以直接调用该 JSON API，不需要解析网页；
- 这是从当前公开前端行为得到的**非官方契约**，随时可能变化；
- 适配器必须做严格 schema 校验、超时、限流、退避和清晰降级；
- 实施前应确认该服务允许当前账户以程序方式调用；
- FlySMS 适配器应被标记为 `experimental`，不能影响 TOTP/Outlook 的可用性。

## 3. 技术选型

| 层次 | 选择 | 原因 |
|---|---|---|
| 语言 | Python 3.12 | 与三份参考项目一致，生态成熟，开发和维护成本低 |
| Web | FastAPI + Uvicorn | API schema、参数校验、错误模型和 OpenAPI 方便 |
| HTTP | HTTPX AsyncClient | Graph/FlySMS 都只需少量异步 REST 请求 |
| TOTP | PyOTP | 标准实现并有 RFC 测试向量 |
| Microsoft auth | MSAL Python | 正确处理 OAuth、silent acquire、refresh 与 cache |
| Graph 调用 | 直接 REST | 避免完整生成式 SDK 的体积与依赖 |
| UI | Jinja2 + 原生 JS/CSS | 无 Node 构建链，界面需求简单 |
| 配置 | YAML/TOML 元数据 + secret files | 配置可读，敏感值不入仓库 |
| 部署 | PyInstaller 单文件程序 | 不要求 VPS 安装 Python、Docker 或 Node，配置和 secret 外置 |
| TLS 边界 | VPS 已有反向代理 | 本项目只监听 loopback HTTP，不生成或管理代理配置 |
| 测试 | Pytest + HTTPX MockTransport | 单元、契约和 API 测试均容易 |

### 3.1 轻量预算

建议将下列指标作为工程预算，而不是硬性承诺：

- 单 app worker；
- app 空闲 RSS 目标不超过约 128 MiB；
- app 可运行在 512 MiB VPS，推荐 1 GiB；
- 不运行数据库服务、Redis、Node 或浏览器；
- 不后台全量同步邮箱；
- TOTP 本地请求目标小于 50 ms；
- 单次上游等待最长 30 秒。

## 5. 统一领域模型

### 5.1 来源配置

每个来源使用稳定别名，例如：

- `github_totp`
- `outlook_primary`
- `icloud_pickup`

调用方只看到别名，不看到 secret、真实 token 或完整取件 URL。

```text
CodeSource
- id
- display_name
- kind: totp | microsoft_graph | flysms
- enabled
- extractor_rules
- non_secret_metadata
- secret_refs
```

### 5.2 Provider 接口

概念接口：

```python
class CodeProvider(Protocol):
    async def get_code(self, request: CodeRequest) -> CodeResult: ...
```

`CodeRequest`：

- `source_id`
- `not_before`：只接受该时间之后的邮件；
- `wait_seconds`：没有新邮件时最多轮询多久；
- `min_ttl`：TOTP 至少还需有效多少秒；

`CodeResult`：

- `code`
- `source_id`
- `kind`
- `observed_at`
- `received_at`（邮件来源）
- `valid_from` / `expires_at` / `remaining_seconds`（TOTP）
- `freshness`
- `evidence`：受控的发件人、主题、消息指纹等，不含正文和上游 token。

## 6. 三种来源的详细设计

### 6.1 TOTP Provider

输入来源：

- 通过部署 secret file 保存 Base32 secret；或
- 初始化 CLI 导入 `otpauth://` URI，再保存为受保护配置。

运行规则：

1. 解析并验证 secret；
2. MVP 固定只返回六位 TOTP；
3. 默认兼容 SHA-1 / 30 秒，也允许从 `otpauth://` 读取 algorithm/period；
4. 返回当前 code、窗口起止时间、剩余秒数；
5. 默认 `min_ttl=5`。如果只剩不到 5 秒，可等待进入下一个时间窗后再返回，避免调用方拿到马上失效的码；
6. 响应头必须为 `Cache-Control: no-store`。

不推荐设计：

```text
GET /totp?secret=...
```

因为 secret 会进入代理、浏览器历史和访问日志。

MVP 推荐只支持“预先配置的来源别名”。如果未来确实需要临时 secret，可增加默认关闭的 `POST` JSON 接口，并确保请求体不记录日志。

### 6.2 Microsoft Graph Provider

#### 授权方式

推荐主路径：

1. 注册自己控制的 Microsoft 应用；
2. 支持个人 Microsoft Account；
3. 开启 public client/device flow；
4. 只申请 delegated `Mail.Read`；
5. 通过一次性 CLI 在浏览器完成 Device Code Flow；
6. 将结果写入持久化 MSAL token cache；
7. 服务运行时始终先 `acquire_token_silent()`。

建议 authority：

```text
https://login.microsoftonline.com/consumers
```

适用于仅个人 Outlook/Hotmail 账户；如果未来同时支持组织账户，再评估 `common`。

#### 对现有四段式凭据的处理

对话中给出的字符串疑似：

```text
email ---- password ---- client_id ---- refresh_token
```

处理原则：

- **不使用、不存储 password**；
- 已有 refresh token 只可作为一次性迁移候选；
- refresh token 必须与原 `client_id`、授权范围和账户绑定；
- 它是否拥有 `Mail.Read` 不能只靠字符串判断；
- 即使能迁移，也推荐最终改为自己注册的 app + Device Code Flow；
- 当 token cache 返回 `interaction_required` 时，在 UI/API 明确提示重新授权，不尝试密码登录。

#### 邮件读取流程

1. 静默获取 Graph access token；
2. 请求 Inbox 最近少量邮件：

```http
GET https://graph.microsoft.com/v1.0/me/mailFolders/inbox/messages
  ?$top=10
  &$orderby=receivedDateTime desc
  &$select=id,subject,from,receivedDateTime,bodyPreview,internetMessageId
Prefer: outlook.body-content-type="text"
```

3. 在本地按 `not_before`、发件人白名单和主题规则筛选；
4. 先从 subject/bodyPreview 提取；
5. 必要时仅对候选邮件再取正文，而不是拉取整个邮箱正文；
6. 不标记已读、不修改邮件；
7. 只保留请求期间的内存数据，响应后丢弃正文。

不优先依赖复杂 `$filter + $orderby`，因为 Graph 对二者组合有顺序限制，错误时会返回 `InefficientFilter`；小范围拉取后本地筛选更可控。

### 6.3 FlySMS Provider

推荐流程：

1. 取件 email/token 存在 secret file，不保存原始 fragment URL；
2. 首先调用 `/messages/latest`；
3. 若最新邮件早于 `not_before` 或不符合提取规则，再按需读取摘要列表和某封详情；
4. 使用以下头部，不把凭据放 URL：

```http
Authorization: Bearer <token>
X-Mailbox-Email: <email>
Accept: application/json
```

5. 每个来源设置独立并发锁，避免页面和 API 同时触发重复请求；
6. 尊重 `Retry-After`，遇到 429 不忙等；
7. 严格验证 JSON 类型、字段长度、时间和数组规模；
8. 不直接把第三方 HTML 正文渲染到本站；MVP 只转换为纯文本做提取；
9. 设置短连接超时、总超时和有限重试；
10. 若接口契约变化，返回 `UPSTREAM_SCHEMA_CHANGED`，不猜测数据。

建议错误映射：

| 上游状态 | 本服务错误 |
|---|---|
| 401 | `SOURCE_CREDENTIALS_INVALID` |
| 403 | `SOURCE_EXPIRED_OR_DISABLED` |
| 404 | `NO_MESSAGE` |
| 429 | `SOURCE_RATE_LIMITED` |
| 502/非法 JSON | `UPSTREAM_SCHEMA_CHANGED` |
| 503 | `SOURCE_SYNCING` |
| 网络超时 | `UPSTREAM_TIMEOUT` |

## 7. 验证码提取策略

单纯对正文执行 `\d{6}` 很容易把订单号、日期、金额或尾号误当验证码。

### 7.1 基础规则

默认候选正则：

```regex
(?<!\d)(\d{6})(?!\d)
```

但候选必须经过评分：

1. 邮件时间必须满足新鲜度窗口；
2. 发件人白名单匹配；
3. 主题中的候选优先于正文；
4. 候选附近出现 `验证码`、`校验码`、`verification code`、`security code`、`OTP` 等关键词时加分；
5. `<script>`、`<style>`、URL、CSS 和隐藏内容不参与提取；
6. 同一封邮件有多个高分候选且无法判定时返回 `AMBIGUOUS_CODE`；
7. 没有满足条件的候选返回 `NO_FRESH_CODE`，绝不返回最近任意六位数。

### 7.2 来源级规则

每个来源允许配置：

- 发件人邮箱/域名白名单；
- 主题关键词；
- 自定义带命名组的 regex；
- 最大邮件年龄；
- 是否允许通用 fallback；

例如：

```yaml
extractor:
  senders:
    - "no-reply@example.com"
  subject_keywords: ["verification", "验证码"]
  patterns:
    - '(?i)(?:code|验证码)\D{0,20}(?P<code>\d{6})'
  max_age_seconds: 600
  allow_generic_fallback: true
```

## 8. API 草案

所有 `/api/v1/*` 接口都要求：

```http
Authorization: Bearer <CODE_RELAY_API_TOKEN>
```

密钥不得出现在 URL。

### 8.1 来源列表

```http
GET /api/v1/sources
```

只返回非敏感信息：来源 ID、显示名、类型、是否可用、是否需要重新授权。

### 8.2 获取验证码

```http
GET /api/v1/codes/{source_id}
    ?not_before=2026-07-30T03:00:00Z
    &wait_seconds=20
    &min_ttl=5
```

示例响应：

```json
{
  "source_id": "outlook_primary",
  "kind": "email",
  "code": "123456",
  "freshness": "fresh",
  "observed_at": "2026-07-30T03:00:08Z",
  "received_at": "2026-07-30T03:00:05Z",
  "valid_from": null,
  "expires_at": null,
  "remaining_seconds": null,
  "evidence": {
    "sender": "no-reply@example.com",
    "subject": "Your verification code",
    "message_fingerprint": "sha256:..."
  }
}
```

TOTP 响应会包含 `valid_from`、`expires_at` 和 `remaining_seconds`。

调用示例：

```bash
curl --fail-with-body \
  -H "Authorization: Bearer ${CODE_RELAY_API_TOKEN}" \
  'https://codes.example.com/api/v1/codes/outlook_primary?not_before=2026-07-30T03%3A00%3A00Z&wait_seconds=20'
```

### 8.3 状态码

| HTTP | 场景 |
|---|---|
| 200 | 成功得到验证码 |
| 401 | 本服务密钥无效 |
| 404 | 来源不存在或等待结束仍无符合条件的邮件 |
| 409 | 找到多个无法判定的验证码 |
| 422 | 参数或来源配置非法 |
| 424 | 来源凭据失效/需重新授权 |
| 429 | 本服务或上游限流 |
| 502 | 上游错误或 schema 变化 |
| 503 | 来源同步中/临时不可用 |
| 504 | 等待上游超时 |

统一错误体：

```json
{
  "error": {
    "code": "NO_FRESH_CODE",
    "message": "No matching code arrived after not_before",
    "retryable": true,
    "retry_after_seconds": 2,
    "request_id": "..."
  }
}
```

### 8.4 缓存约束

所有带验证码、邮件元数据和认证信息的响应都发送：

```http
Cache-Control: no-store, private
Pragma: no-cache
X-Content-Type-Options: nosniff
```

生产环境 OpenAPI `/docs` 应关闭或置于同一鉴权之后。

## 9. 前端方案

### 9.1 页面

1. **登录页**：只接受网页登录密码；
2. **Dashboard**：每个来源一张卡片；
3. **状态区**：正常、正在获取、无新验证码、需重新授权、上游限流；
4. **来源详情（只读）**：掩码邮箱、来源类型、最近成功时间；
5. **重新授权提示**：只给出管理员 CLI 操作说明，不在网页展示 token。

### 9.2 交互

- TOTP 卡片显示六位码、30 秒进度环和复制按钮；
- 邮箱卡片使用“获取最新验证码”，可选择等待 20 秒；
- 代码复制后给短暂反馈；
- 切换页面或超时后隐藏已显示代码；
- 不在 localStorage/sessionStorage 保存 API token、上游 token或验证码；
- 页面不展示完整邮件正文；

- 机器调用：高熵 Bearer Token；
- 网页登录：独立密码，服务端保存 Argon2id hash；

- session 默认 8 小时，支持主动退出；
- 登录接口单独限流。

## 10. 安全设计

### 10.1 威胁模型

本服务中任意一种泄漏都可能等价于账户接管的一部分：

- TOTP Secret 可无限生成当前/未来验证码；
- Outlook refresh token 可长期读取邮箱；
- FlySMS token 可读取临时邮箱；
- 本服务 API token 可直接获取聚合后的验证码。

因此它不应被当作普通“工具页”，而应按一个小型凭据保险库保护。

### 10.2 必须项

1. **立即更换已暴露凭据**
   对话中已经出现 Outlook 密码、refresh token 和 FlySMS key。它们不应再进入代码、配置示例或文档。开始联调前应更改 Outlook 密码、撤销旧会话/refresh token，并在 FlySMS 可行时更新取件 token。

2. **仅 HTTPS 对外**
   CodeRelay 本身只监听 `127.0.0.1`；公网 TLS 由 VPS 已有反向代理终止，loopback 端口不得直接暴露。

3. **高熵 API Token**
   至少 32 随机字节；支持两把 token 并行一段时间，以便无停机轮换；服务端只保存 hash。

4. **来源别名代替 secret 入参**
   正常 API 请求绝不携带 TOTP Secret、refresh token 或取件 key。

5. **日志脱敏**
   不记录 `Authorization`、Cookie、请求体、验证码、邮件正文、token cache；邮箱只在必要时掩码显示。

6. **限流与并发合并**
   对登录、API key、IP、单个来源分别限流；同一来源并发获取合并为一次上游请求。

7. **最小权限**
   Graph 只申请 delegated `Mail.Read`，不用 `Mail.ReadWrite`；不使用账户密码。

8. **CORS 默认关闭**
   只有确实存在浏览器跨域调用时，才显式允许固定 origin；绝不使用 `*` + credentials。

9. **前端防护**
   CSP、frame-ancestors、nosniff、Referrer-Policy；第三方邮件 HTML 不直接嵌入主页面。

10. **文件与进程权限**
    secret files 和 token cache 仅 CodeRelay 专用 Linux 用户可读写，设置为 `0600`；运行目录设置为 `0700`。

### 10.3 网络暴露的两个模式

**模式 A，安全性最高：** Tailscale/WireGuard 私网 + 应用 Bearer Token，不真正暴露公网业务端口。

**模式 B，符合当前“公网可访问”要求：** 公网域名 + VPS 已有 HTTPS 反向代理 + 应用层 token/session + 限流；UI 可再叠加访问控制，API 继续使用独立 Bearer Token。

若另一个项目也在可加入 Tailscale 的服务器上，优先选模式 A。

## 11. 配置与敏感数据存储

### 11.1 非敏感配置

可以进入仓库：

```yaml
sources:
  github_totp:
    type: totp
    display_name: GitHub
    secret_file: /run/secrets/totp_github

  outlook_primary:
    type: microsoft_graph
    display_name: Outlook
    client_id_file: /run/secrets/ms_client_id
    token_cache_file: /data/msal-cache.enc
    extractor: {}

  icloud_pickup:
    type: flysms
    display_name: iCloud Pickup
    email_file: /run/secrets/flysms_email
    token_file: /run/secrets/flysms_token
    extractor: {}
```

### 11.2 敏感配置

不得进入仓库：

- API token/hash；
- UI 密码 hash；
- session signing key；
- TOTP Secret；
- Microsoft client ID（本身不是密码，但与账户凭据一起管理更简单）；
- MSAL token cache；
- FlySMS email/token；
- Outlook 密码（本项目完全不保存）。

### 11.3 MSAL cache

MVP 推荐：

- cache 存在独立持久化 volume；
- 原子写入（临时文件 + fsync + rename）；
- 进程内锁；
- app 使用单 worker，避免跨进程同时覆盖；
- `0600` 权限；
- 可使用 AES-GCM 加密，主密钥来自单独 secret file；
- 备份 cache 时同时保证备份加密，主密钥单独保管。

需要明确：如果攻击者已经同时取得 CodeRelay 进程权限和主密钥，加密文件无法阻止其解密；文件加密主要降低磁盘快照、误备份和离线泄漏风险，不能替代 VPS 加固。

## 12. 部署方案

### 12.1 单文件程序

```text
公网 HTTPS
    │
VPS 已有反向代理（项目外）
    │ 127.0.0.1:8787
    ▼
/opt/coderelay/coderelay
/opt/coderelay/config.toml
/opt/coderelay/secrets/  (0700，文件 0600)
/opt/coderelay/data/     (0700，MSAL cache)
```

- 使用 `scripts/build-binary.sh` 和 `coderelay.spec` 生成 `dist/coderelay`；
- 构建环境必须与 VPS CPU 架构一致，并使用兼容或更旧的 glibc；
- VPS 不需要安装 Python、Docker 或 Node；
- 程序只监听 loopback；
- 配置、secret 和动态 MSAL cache 不打包进二进制；
- 升级时替换可执行文件并重启进程，保留配置与 data 目录。

### 12.2 VPS 基线

- Ubuntu/Debian LTS；
- SSH key 登录，关闭密码 SSH；
- 防火墙只开 22/80/443，或私网模式只开必要端口；
- 自动安全更新；
- `systemd-timesyncd`/chrony 正常同步；
- 防火墙不开放 CodeRelay 的 loopback 监听端口；
- 定期备份配置和 token cache，备份不包含明文 secret；
- 域名 DNS 与 TLS 续期监控。

### 12.3 健康检查

- `/health/live`：进程是否存活，不访问上游，不含敏感数据；
- `/health/ready`：配置和本地 cache 是否可读，不泄漏具体账户；
- 上游状态只在鉴权后的 `/api/v1/sources` 展示。

## 13. 可靠性策略

- HTTP connect/read/total timeout 分离；
- 只对网络错误、部分 5xx 做有限重试；
- 401/403 不自动重试；
- 429 严格尊重 `Retry-After`；
- per-provider semaphore 和 per-source lock；
- 邮件等待采用有限轮询，例如 2 秒间隔、最多 30 秒；
- 请求取消时停止轮询；
- 不保存长期邮件 cache，仅做 1～2 秒的请求合并/短缓存；
- 所有时间内部使用 UTC；
- 每个响应和错误带不敏感的 `request_id`；
- FlySMS schema 变化与其他 Provider 隔离。

## 16. MVP 验收标准

满足以下条件才视为完成：

1. 未授权请求无法访问任何验证码或来源详情；
2. API key、Cookie、上游 token、TOTP Secret、验证码不出现在普通日志；
3. TOTP 与 RFC 测试向量一致，并返回准确剩余时间；
4. 部署前明确检查 VPS 的 NTP/chrony 同步状态；
5. Outlook 在服务重启后可通过 MSAL cache 静默读取；
6. Outlook 只使用 `Mail.Read`，不使用密码、不修改邮件；
7. 带 `not_before` 的请求不会返回更早的邮件验证码；
8. 多个候选无法判定时返回歧义错误，不随机选一个；
9. FlySMS 遇到 429 会尊重 `Retry-After`；
10. FlySMS 接口变化不会导致返回未校验数据；
11. 前端不把机器 API token 或验证码写入 localStorage；
12. 所有敏感响应禁止缓存；
13. app 只监听 loopback，公网只能经过现有 HTTPS 反向代理；
14. 仓库 secret scan 无真实凭据；
15. 有一份可重复执行的部署、备份、恢复和密钥轮换说明。

## 17. 主要风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 对话中的凭据已暴露 | 账户/邮箱被读取 | 实施前先轮换，仓库从不写入旧值 |
| 旧 refresh token 无 `Mail.Read` | Graph 无法读正文 | 使用自有 app 重新 Device Flow 授权 |
| FlySMS 是非官方契约 | 随时失效 | 独立 adapter、schema 校验、契约测试、experimental 标识 |
| 六位数字误识别 | 返回错误验证码 | 时间 + 发件人 + 上下文评分，歧义即失败 |
| 返回旧邮件验证码 | 自动化登录失败/锁号 | `not_before`、最大年龄、有限等待 |
| VPS 时间漂移 | TOTP 错误 | NTP/chrony、启动检查、监控 |
| 公网 API key 泄漏 | 所有来源被读取 | HTTPS、hash 存储、短日志、轮换、限流、可选私网 |
| token cache 损坏/覆盖 | Outlook 需重登 | 单 worker、锁、原子写入、加密备份 |
| 邮件 HTML 恶意内容 | XSS/数据外带 | 只转纯文本，不在主页面直接渲染 |
| 上游限流 | 请求失败 | 请求合并、短缓存、Retry-After、最大等待 |

## 18. 已确认的实施决定

1. TOTP 使用预配置来源别名，不在常规 API 中接收任意 `2fasecret`；
2. 服务提供公网 HTTPS API，应用层使用独立 Bearer Token；
3. Microsoft 使用自有 app + Device Code Flow + delegated `Mail.Read`；
4. MVP 只返回六位验证码，邮件来源支持发件人与主题规则；
5. 邮件 API 支持 `not_before` 和最长 20～30 秒等待；
6. 部署产物为单文件 Linux 可执行程序；不交付 Docker/Caddy 配置，TLS 使用 VPS 现有设施。

总体架构保持不变，部署边界调整为“CodeRelay 只负责 loopback HTTP 应用本身”。
